# Audit complet du projet — 2026-11-03 (rc23)

Auteur : agent testeur (accès ssh aux caméras .11 IPCAMERA2 et .24 IPCAMERA1, toutes deux en 3.0.1-rc23 depuis la flash).
Méthode : lecture du dépôt au commit `bd4bfa3` (714 commits), mesures en direct sur les deux caméras le 2026-11-03 au soir,
journaux CI GitHub. Chaque constat donne sa preuve (fichier:ligne, commande ou mesure). Rien n'a été modifié sur les caméras
pendant l'audit, sauf l'enregistreur de nuit `/tmp/nightcam.sh` (RAM).

## 1. Verdict

Le projet est **fonctionnellement complet et sain** : démarrage depuis la flash, watchdog matériel, vidéo H.265/H.264
matérielle, sous-flux, JPEG matériel, flux HTML5, MQTT/Home Assistant, mDNS, auth + CSRF, export/import, mises à jour web.
Les surfaces réseau sont réduites (22, 80, 554, 5004/udp, 5353/udp seulement). La RAM tient (~20 Mo disponibles sur 59 Mo).

Les risques restants ne sont plus des fonctions manquantes mais : **(a)** des fonctions jamais testées sur caméra,
**(b)** quelques défauts de robustesse (valeurs de config non protégées, réponse d'import vide, CGI lents par moments),
**(c)** l'hygiène du dépôt (pas de fichier LICENCE, binaires préconstruits d'origine non documentée, CI rouge 14 fois sur 19),
**(d)** une documentation devenue trop volumineuse pour un nouvel utilisateur.

## 4. Sécurité

Points solides : authentification sur toutes les pages, snapshots et RTSP (401 sans identifiants, vérifié) ; jeton CSRF
par démarrage, contrôlé sur toutes les commandes `action.cgi` qui modifient (liste blanche des lectures,
`action.cgi:1150`) et sur `update.cgi`, `flashinstall.cgi`, `config_exchange.cgi`, `camcontrols.cgi` ; analyse des
paramètres sans injection (`func.cgi:146-176` : nom validé, `\ " ` $` échappés avant `eval`) ; telnet, FTP et ONVIF
éteints ; seulement 5 ports ouverts.

| # | Gravité | Constat | Preuve | Correction proposée |
|---|---|---|---|---|
| S1 | Moyenne | **Valeurs écrites sans protection dans des fichiers sourcés par le shell root.** `MQTT_USER`, `MQTT_PASSWORD` (et `apiToken`/`userChatId` Telegram) sont écrits tels quels par `rewrite_config` (`KEY=valeur`, non quoté), puis `mqtt.conf` est sourcé (`scripts/mqtt-bridge.sh:122`, `controlscripts/mqtt-bridge:14`, `telegram.conf` dans `telegram-bot-daemon.sh:8`). Un mot de passe contenant une espace ou `$(…)` casse la config ou s'exécute en root. Exploitable seulement par un utilisateur déjà authentifié avec jeton CSRF (donc déjà root) : c'est surtout un **bug fonctionnel** (mot de passe MQTT avec espace = bridge cassé) et une faiblesse de défense en profondeur. | `scripts/action.d/integrations.sh:17-19, 92-97, 140-141, 176-177` ; `scripts/action.d/system.sh:413-418` | Écrire les valeurs entre quotes simples échappées (`KEY='va'\''leur'`) dans `rewrite_config`, ou lire ces fichiers avec un parseur clé=valeur au lieu de `.` ; test de non-régression avec un mot de passe `a b$(x)`. |
| S2 | Faible | `csrf_check` d'`action.cgi` laisse passer si aucun jeton n'existe (`[ -z "$_csrf_stored" ] && return 0`). En pratique `csrf_guard` en crée un juste avant. | `action.cgi:1110` | Échouer fermé si le jeton est absent. |
| S3 | Faible | HTTP en clair (identifiants Basic Auth sur le réseau local) ; documenté comme limite. | README « What 3.0 does not do » | Garder ; rappeler de ne pas exposer la caméra hors du LAN. |
| S4 | Info | La config Frigate générée contient le mot de passe caméra en clair (une option `redact=1` existe pour la partager). | `state.cgi?cmd=frigateyaml`, `state.cgi:1445` | Par défaut, utiliser `{FRIGATE_RTSP_PASSWORD}` (variable de secrets Frigate). |
| S5 | Info | Le mot de passe des deux caméras de test est trivial. | | Changer de mot de passe avant tout usage hors test ; l'assistant pourrait refuser les mots de passe trop courts. |

## 7. Tests et CI

- 378 tests Python, bonne couverture des scripts, du serveur RTSP (tests hôte), de l'UI (câblage, bundle CSS) et du budget flash.
- **CI rouge 14 fois sur les 19 dernières exécutions.** Le seul échec actuel est
  `test_regressions.WebUiCss.test_purged_bulma_keeps_every_class_the_ui_uses` : la classe `has-text-weight-semibold`
  est utilisée mais purgée du CSS. Une CI rouge en permanence masque les vraies régressions (cas de la rc22 qui ne compilait pas).
- Les 3 suites Node sont des scripts `node:assert` (79 assertions au total, pas de `test()`) : elles testent bien, mais un échec arrête la suite au premier assert ; passer à `node:test` donnerait un rapport par cas.
- Manquent : un test qui écrit un mot de passe MQTT avec espace (S1), un test de réponse de l'import JSON, un test de cohérence fps entre `rtspserver.conf` et `frigateyaml`.

## 8. Documentation

- README complet et honnête sur les limites, mais long (434 lignes) et orienté développeur ; il annonce « 15 fps by default » alors que la config livrée est `fps=25`.
- `test-queue.md` (1 870 lignes) sert à la fois de file de tests, de journal et de compte rendu : difficile à exploiter. Proposition : une section par version, archiver ce qui est clos dans `test-queue-archive.md`.
- `docs/known-issues.md` daté du 2026-10-31 : à mettre à jour avec les constats rc21-rc23.
- Le projet claude.ai contient 84 notes, dont ~50 périmées (nettoyage en attente d'accord).
- Manque : une page « j'ai un TC100, que faire » (installation en 5 étapes, sans terminal).
