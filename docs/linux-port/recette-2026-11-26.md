## FAIL lines, as they came (with what `recette.log` shows around each)

1. **B1-ONVIF pwd-file, both cameras: `user.pwd` mode `-rw-r--r--` on IPCAM2 and `-rwxr-xr-x` on IPCAM1** (expected 0600).
   Real on the cameras as far as the tester can see (file dated 15/11 on IPCAM2, 16 bytes; content not read). The bench
   does not write `/mnt/config`, so nothing was changed. For the implementer: who creates the file and with which mode.
2. **AUDIT-1116-RTSP stall-exit (IPCAM2): no exit in 12 s of SIGSTOP + 40 s of wait, no `no frame for` line, `exit3` +0.**
   **Undetermined, camera or bench.** The bench starts the server with `RTSP_CAPTURE_STALL_S=5 sh
   /mnt/tc100test/rtsp-launch.sh`; to check: that the variable reaches the process (`/proc/PID/environ`) and that the
   launcher does not reset it; and that a SIGSTOPped process, resumed after 12 s, still takes the 12 s as a stall
   (the clock may be read only by the stopped thread).
3. **W1-PRIVFILL pp-privacy (IPCAM2): `pp_ms` 3 without privacy, 2149 with `/tmp/tc100_privacy`** (3 STAT lines each;
   the file was removed afterwards). **Undetermined.** The first STAT windows after the file appears may include the
   switch itself; the check should be read against the W1 entry before it is called a regression.
4. **AUDIT-1116-VENCIRQ irq-sample (IPCAM2): `irq +3135 for 16 pictures` (safe run) and `+3141 for 115 pictures`
   (disruptive run).** **Bench defect, A and C below:** the pictures count is the difference of two single STAT windows,
   not the pictures of the 60 s (a window holds about 80 to 120 main and as many sub pictures). On IPCAM1 the check was
   a SKIP (no picture counted). The interrupt count per kill cycle (irq-follows-kills, 83 to 149 per cycle) is fine.
5. **AUDIT-1116-USB wpa-reassociate (IPCAM2): `5/5 reassociate commands ok, 4/5 link drops seen, 5/5 back with address and
   route`.** The link did come back every time; one reassociate was too short for the bench to see a drop. Bench
   threshold, not a Wi-Fi failure.
6. **CLEANUP-1124 start-lines (safe runs on both cameras): `direct capture lines 0`.** The start lines had left the
   current log by rotation (`tc100_rtsp.log.1` holds none either after 6 to 13 h). After the bench restarted the video
   server in the disruptive run, the same check **PASSed**. So it is a time-of-reading effect: the check should look
   right after a start or read the rotated file, or the entry should say so.

## Bench defects found (the bench is the first thing to fix before the next run)

- **A. Infinite kill loop on a real camera (stopped by the tester after 62 kill + start cycles in 13 min).**
  `wait_stat`, `wait_gone` and the two other wait helpers (`recette.sh` lines 208-264) use the global variable `_i`
  as their counter, and `kill_cycles` (line 364) and `c_stream_cycles` (line 439) use `_i` as theirs: after each
  helper `_i` is back at 5 or 6, so `_i < RECETTE_KILLS` is never false and the loop runs for ever, killing the
  video server every 15 s. **Fix:** rename the counter in the helpers to `_wi` (`sed '205,270s/_i\b/_wi/g'`, 13
  lines); with that single change the tester's run did exactly 10 kills and 20 stream cycles. The 62 cycles of the
  loop were all clean (`picture failed` 0, `exit3` 0, interrupts counted after each start): useful as a soak, not as
  intended. Check the other loops with the same pattern (lines 504, 547, 667, 729) after any helper that sets `_i`.
- **B. No `scp` on the cameras** (Dropbear without it; OpenSSH `scp` needs the remote `scp` or SFTP): the first
  step `copy recette.sh` fails with `lost connection`. The tester used a small `scp` replacement over `ssh cat`; the
  host script could do the copy with `ssh host 'cat > file' < file` and the fetch with `ssh host 'cat file'`.
- **C. irq-sample** compares single STAT windows (see FAIL 4).
- **D. The summary FAIL count** is higher than the number of `RESULT ... FAIL` lines (6 vs 3, 8 vs 5, 5 vs 2).
- **E. start-lines** reads only the current log (FAIL 6).
- **F. The host script needs the ssh key options of the tester's machine** (`-i`, `IdentitiesOnly`, known-hosts file):
  a `RECETTE_SSH_OPTS` variable would avoid a wrapper in `PATH`.
- The host script process does not survive between two tester shell calls; the camera part is detached and finishes
  by itself, so the results are fetched from the run folder (`/tmp/recette-<date>/`).
