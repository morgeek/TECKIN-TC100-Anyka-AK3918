# tc100_rtsp CPU measured on two cameras, 2026-11-11 (read-only capture)

Same capture as the background summary: 2 h 05 min, 25 samples 5 min apart, utime / stime of tc100_rtsp (100 Hz
ticks), minor faults, plus the program's own STAT lines (every 5 s, in /tmp/logs/tc100_rtsp.log) read at the end.
Firmware 3.0.0, daylight, one RTSP client, no recording, no sub stream client.

Running configuration (environment of the process; nothing else set, so the code defaults apply for capture mode:
no RTSP_DIRECT, RTSP_CACHED, RTSP_ZEROCOPY, RTSP_PROFILE, and no RTSP_UDPSG: RTP goes through send_pkt / rtp_out):
RTSP_SENDER_THREAD=1, RTSP_ABR=1, RTSP_MD_ENC=1, RTSP_LOWLIGHT_FPS=1, RTSP_NIGHTSTYLE=1, RTSP_AUDIO_AGC=1,
RTSP_AUDIO_HPF=1, RTSP_AUDIO_DUCK=1, RTSP_ALSA_DIRECT=1, RTSP_REC_AAC=1, RTSP_QMAX=1024 (.24 also RTSP_VBR=1).
Encoder log: "free encoder: H.265 1920x1080 (source stride 1920), 1600 kbit/s, 25 fps, GOP 50, QP 25-48".
2 or 3 threads, VmRSS 1.2 MB (the picture buffers are in the reserved encoder pool / CMA, not counted).

## CPU of tc100_rtsp, average and spread of the 24 five-minute intervals

| | .11 | .24 |
|---|---|---|
| CPU (utime + stime) | 16.0 % (15.1-16.7) | 17.1 % (15.1-18.3; 11.5 % in the last interval, below) |
| of which system time | 10.4 % (9.5-11.0) | 11.0 % (9.6-12.1) |
| of which user time | 5.6 % | 6.1 % |
| minor page faults / s | 101 (95-113) | 125 (105-142) |
| whole CPU busy at the same time | 22.1 % | 24.8 % |

The .24 last interval (15:50-15:55, dusk) fell to 11.5 % / 7.3 % system / 70 faults/s; its STAT lines at the end of
the capture show 10 frames/s ("low light: total gain 26x, sensor 10 fps"): CPU follows the frame rate.

## Per frame (.11, 24.5 frames/s all along: STAT "cap 122-125" per 5 s)

| | per frame |
|---|---|
| CPU | ~6.5 ms (system ~4.2 ms, user ~2.3 ms) |
| minor faults | ~4.1 |
| encoded size | ~8 kB (980 kB per 5 s, 1.6 Mbit/s) |
| wall time in the encode step (STAT enc_ms 3620-3690 per 5 s) | ~30 ms (about 74 % of wall time) |
| main loop send (snd_ms ~90-120 per 5 s) | ~0.9 ms |
| sender thread (snd_thr_ms ~360-380 per 5 s) | ~3 ms |
| post-processing (pp_ms), sub picture (sub_ms) | ~0 |

On .24 at 10 frames/s: enc_ms 1430-1530 per 5 s (~30 ms per frame, same), snd_thr_ms 156-190, snd_wait 3-96.

Most of the encode step is waiting for the hardware (it is 30 ms of wall time against ~6.5 ms of CPU per frame);
what part of the 4.2 ms of system time per frame comes from which call (select, DQBUF, encoder, send, QBUF) is **not
measured yet**: the program has a profiler for exactly that (RTSP_PROFILE=1 adds a "PROF sys ms" line every 5 s) but
it needs a restart of tc100_rtsp with that variable, which was not done during this read-only capture.

## Per thread, 60 s read at 17:15 (two /proc/<pid>/task/*/stat reads 60 s apart, same STAT frame rates)

| thread | .11 (24.5 frames/s) | .24 (10 frames/s) |
|---|---|---|
| main thread (capture, encode, audio, RTSP, ISP tuning) | 10.9 % (user 5.5, system 5.4), 98 faults/s | 8.3 % (user 4.2, system 4.1), 52 faults/s |
| sender thread (RTSP_SENDER_THREAD, RTP out) | 4.4 % (user 0.6, system 3.8), 12.5 faults/s | 1.8 % (user 0.2, system 1.6), 5 faults/s |
| third thread (.24 only, backchannel / talk) | - | ~0 % |

Read as cost = fixed + per frame (two cameras, same firmware, one minute each, so a rough fit):
- main thread: ~1.8 ms of CPU per frame, plus **~6.5 % of a CPU that does not depend on the frame rate**;
  faults ~3.2 per frame plus ~20 / s.
- sender thread: ~1.8 ms of CPU per frame, ~90 % of it system time, for ~6 RTP packets per frame (8 kB): ~0.3 ms
  of system time per packet (one RTSP client over TCP interleaved or UDP, Wi-Fi).

The fixed share is the surprise: at 10 frames/s the main thread still uses 8.3 %. Candidates in the loop that run on
time, not on frames: the microphone path (8000 samples/s through the level meter, adsp_sample: AGC, high-pass, duck,
then A-law, and lis_write), the select wake-ups when no frame comes (the microphone pipe is added to the set after
0.25 s without video), the 5 s STAT / log tick, the ISP tuning and exposure loops, talk_tick / lis_scan / live_scan.

## Not measured, would decide between the hypotheses

- PROF line (per call system time) on one camera, 10 min.
- Where the ~4 minor faults per frame come from (perf is not on the camera; /proc/<pid>/stat minflt before and after
  one frame, or per thread in /proc/<pid>/task/*/stat).
- Audio path CPU on its own (AGC, HPF, AAC for the recorder while not recording).
