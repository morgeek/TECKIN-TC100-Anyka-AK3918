# tc100_rtsp measured with its profiler, .11 on 3.0.1-rc37, 2026-11-11 evening (owner's OK)

H.265 1080p, ~1.6 Mbit/s (ABR; the same byte rate at both frame rates), one RTSP client over TCP (192.168.1.25) that
takes the audio track (the microphone is open while sound detection, recording and the Listen button are all off).
rc37 runs **without the sender thread** (`RTSP_SENDER_THREAD` back to opt-in in rtsp-launch.sh, commit 91c408b): one
thread does everything. Per-thread CPU from /proc/<pid>/task/*/stat; system time per call from the program's
`RTSP_PROFILE=1` line (mean of the 5 s lines over the run). Settings restored at the end (25 fps, no profiler).

| | 24 frames/s (10 min) | 10 frames/s (5 min, rtspserver.conf fps 10) | per frame (fit) | fixed (fit) |
|---|---|---|---|---|
| CPU of tc100_rtsp | 15.8 % (user 5.4, system 10.4) | 12.9 % (user 4.3, system 8.6) | ~2.0 ms | **~10.9 %** |
| minor faults / s | 73 | 64 | ~0.6 | ~58 / s |
| encoded bytes per 5 s | 964 kB | 1001 kB | | |

System time per 5 s by call (ms; 500 ms = 10 % of a CPU):

| call | 24 frames/s | 10 frames/s | reading |
|---|---|---|---|
| select (121 / 51 wake-ups per 5 s, all from video, 0 from the microphone) | 130 | 108 | almost fixed: not the cost of the call itself (1.1 then 2.1 ms per wake-up); time charged while the loop sleeps or wakes (interrupts, 100 Hz tick accounting) |
| encode (main) | 189 | 109 | ~1.1 ms per frame + ~50 ms fixed: grows with frame size |
| send (video RTP to the client) | 69 | 90 | follows the bytes, not the frames |
| DQBUF + QBUF | 6 | 3 | negligible |
| other (everything outside the six calls: microphone read, audio RTP, client queue flush, files, ISP loops) | 122 | 122 | **fixed** |
| total | 518 | 434 | ~1.2 ms per frame + ~375 ms fixed (7.5 %) |

So at a constant byte rate, ~75 % of the program's CPU does not depend on the frame rate: ~7.5 % system (other ~2.4 %,
select ~2 %, sends ~1.5 %, encoder fixed part ~1 %) and ~3.5 % user. The fixed page faults (~58 / s) are not from a
per-frame allocation: with the sender thread off there is no `sjob_new` / `free` per frame.
